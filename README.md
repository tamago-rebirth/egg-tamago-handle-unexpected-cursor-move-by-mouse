Emacs でマウスによるカーソルの移動、あるいは C-n, C-p を押してしまってegg/Tamago の変換領域が誤動作しておかしなことになった体験はありませんか？

egg/TAMAGO で入力をしているときに、マウスでカーソルを動かして変換している範囲から出てしまうと、次に SPACE あるいは NEWLINE などの変換動作をするときに内部のデータ構造がおかしくなり、結果として 消すことのできない READ-ONLY の領域が残り、また ！、 |といった余計な文字がバッファ内部に残される。
この困った状況を解決するには、一度ファイルをセーブして、バッファも消去して、再度新たにバッファうに読み込んでREAD-ONLY 領域を読み書きでいきるようにして編集を再開して 余分な ｜、！ を消去しないといけない。
このレポジトリにある m20.el は、マウスの利用をモニターして、egg/TAMAGO による変換中にマウスによりカーソル位置が外に出てしまった場合には、まず egg/TAMAGO による変換を終了して、そのあとでカーソル位置を動かす。これによりegg/TAMAGO によるREAD-ONLYの領域を残すエラーは発生しなくなる。
使い方は cursor-tracking-and-check.el を見てほしい。m20.el をロードして (egg-load-monitor-hooks-extended) を呼ぶことでマウスのトラッキングが始まる。

実はマウスとは関係なく、なぜか私が使っている egg/TAMAGO ではいくつかのカーソルを動かすキーバインドがegg/TAMAGO の管理下になく、C-p, C-n などでも変換領域から出てしまいマウスによるカーソル移動と同じ問題を引き起こす。それを防ぐための binding をしているのが its-exit-wrappers.el である。
このファイルは cursor-tracking-and-check.el からロードされている。emacs の init ファイルからこれをロードしてほしい。

背景： 
文章の編集でキーボードを頻繁に高速に入力して編集しているときに上の問題がよく起こって困っていたが、emacs 29.4 からEmacs 30.2  に移行したところ egg/TAMAGO に少し手を入れないと動作しないことがわかり、その際に上記の問題の原因を追究してこれらのファイルを作った。
実はほとんどマウスをつかっていないのだが、たまに手がマウスに当たってマウスによる位置移動があったときに上の問題が起きることに気づいて、最初はそれを解決しようとこころみた。
最初にマウスカーソルの問題を解決できたと思って利用していたが、そのあとでも同様の問題がおきて不思議に思った。
それは変換が終了してない状態で C-n、C-pあるいはC-vなどを入力したせいだとM20.el が行っているマウス、キーのトラッキングのログを見ることで明らかになった。
マウス、キーのトラッキングは  変数 its-debug-enabled を  non-nil にするとおこなわれて *ITS-DEBUG* というバッファに記録される。
それに気づいてよく使う代表的なカーソル移動キーで、egg/TAMAGO 内部で使われてないキーは、 egg/TAMAGO の変換から抜けてからカーソルを移動するような関数を作り  its-exit-wrappers.el でキーのバインドをしなおした。  
M->, M-< はどうもegg/TAMAGO では 特別な関数にバインドされていて、それを頻繁に使う方はそこのマッピングをコメントアウトしてほしい。
わたしは M-<, M-> はegg/TAMAGO の利用よりも、普通の M-<、M-> のファイルの先頭、最後への移動の方の利用頻度が多いのでこうした。

minibuffer でファイル名の入力をしているときに、ミニバッファの関係ない領域にマウスでカーソルを動かすときに正しく egg/TAMAGO の変換を終了する処理が面倒だったが、今はとりあえず動いている。
minibuffer でのテストとしては次のようなことを行った。
C-x C-f でファイルを編集しようとバッファに読み込むときにファイル名に日本語の入力をして、その途中にカーソルをminibuffer  の右端でクリックして egg/TAMAGO の変換を抜けて、おかしな状況にならないことを確認した。
minibuffer で最初に述べたような READ-ONLY領域が残るようなおかしな状況がおきると事実上 emacs を終了するしかない。

問題の報告：
(setq its-debug-enabled t) で一文字単位でキー、マウスのトラッキングをするデバッグ用ログを残しても、そこそこのCPUであれば性能的に問題はないと思われる。私はそれで原稿を書いている。
時々スローダウンがあるが、それは大体私が使ってる他の言語のモードなどが引き起こす GC のせいだ。
普段この変数を nil にして使っていただいても問題はないと思うが、もし何か不可思議な問題に気づいたときには この変数を t  にして、問題がでたときの  *ITS-DEBUG＊の後ろの方を送付してほしい。
＊注意＊：その際に押したキーがログに残っているので、パスワード、クレジットカード番号などの情報が残っていないように気を付けてほしい。
